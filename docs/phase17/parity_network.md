## Gaps summary

- **Fixed: relay nodes never re-propagated inbound gossip transactions to their other peers (`TestLineNetwork`)**: the Phase 17 network deep pass's investigation into "why is multi-hop propagation untested" found `TxTagHandler` deliberately, permanently returned `ForwardingPolicy::Ignore` for every inbound `TX` group instead of relaying accepted groups onward — a real production gap (not just a test gap): a 3-hop chain A→B→C would have B ingest A's transaction into its own pool but never forward it to C. Fixed by wiring the pre-existing `GossipNode::relay` (`WebsocketNetwork::relay`, already correctly implemented and already used elsewhere — just never called from this handler) into `TxTagHandler::ingest_group`'s post-`Remember`-success path via a new `TxTagHandler::with_relay` builder method, matching go's `TxHandler.postProcessCheckedTxn` exactly (relay only after local `Remember` succeeds, excluding the sender, using the same canonical re-encoding `LocalTxBroadcaster::encode_tx_group` already provides). Wired into both production `TxTagHandler` construction sites (WS-gossip and P2P transports) in `bin/algod-rust/src/commands/participate.rs`. Proven end-to-end by a new 3-node relay-chain integration test, `txn_propagates_across_three_hop_relay_chain` (`crates/node/algo-network/tests/tx_propagation_inproc.rs`), which fails without the fix and passes with it.

- **Outbound dial header-size cap ported; address-bound HTTP transport/client scoped out (issue #1158)**: `TestMaxHeaderSize` moves from `not-implemented` to `matched-1:1` — `ConnectConfig::max_header_bytes` (default 4096, matching go's `wsMaxHeaderBytes`) caps the outbound dial's HTTP upgrade response header size for plain (`ws://`) connections. Neither `tokio-tungstenite` nor `tungstenite` expose an equivalent knob, and there is no way to layer a byte-counting wrapper around just the handshake phase of their dial helpers without changing the resulting stream's type away from what `WsPeer` is built against — so `connect.rs::dial_with_header_cap`/`read_capped_response` reimplement the wire exchange directly against the raw `TcpStream`, reusing tungstenite's own public building blocks (`generate_request`, `derive_accept_key`, `Response::try_parse`) rather than reimplementing HTTP/WebSocket framing from scratch. `wss://` connections fall back to the previous uncapped behavior (capping TLS-ciphertext header bytes would require driving the TLS handshake through the same manual path too). `TestHTTPPAddressBoundTransport`/`TestWebsocketNetworkHTTPClient` were left `not-implemented` pending a deliberate direction call, filed as follow-up issue #1185.
- **Address-bound HTTP transport/client: direction (a) confirmed, `not-implemented` → `out-of-scope` (issue #1185)**: re-investigated whether algod-rust's per-purpose peer-addressed HTTP fetchers should be unified under one shared `HTTPPAddressBoundTransport`/`GetHTTPClient`-equivalent type (direction (b)) or accepted as the parity answer with the go tests marked `out-of-scope` (direction (a)). Beyond the two fetchers #1158 already found (`algo-rest-client::CatchpointDownloader`, `algo-rest-client::http_block_fetcher::HttpBlockFetcher`), this issue searched for and found a **third**: `algo-network::tx_sync_client::HttpTxSyncClient` (issues #774/#792), which also owns its own `peer_addr: String` field and hand-builds `format!("http://{}/v1/{}/txsync", self.peer_addr, ...)` directly, following the identical pattern. Even with three instances of the pattern, direction (a) was chosen: go's `HTTPPAddressBoundTransport` exists specifically so *generic* `http.Client`-consuming code (`makePeerCore`'s `Peer` wiring) can be redirected to a specific peer without that code knowing about peer addressing at all — algod-rust has no such generic consumer; all three fetchers are purpose-built, construct their own request paths directly, and differ substantially in what else they do around the HTTP call (streaming with stall-detection and P2P-transport fallback for `CatchpointDownloader`, response-size-capped GET for `HttpBlockFetcher`, Bloom-filter-encoded POST for `HttpTxSyncClient`). Unifying them under one shared transport type would extract only the trivial "join base_url + path" logic while leaving the substantially different logic in each fetcher untouched — a DRY refactor of already-working code with no new caller to justify it, not the "genuine present or near-term caller" bar the issue set for direction (b). `TestHTTPPAddressBoundTransport`/`TestWebsocketNetworkHTTPClient` reclassified `not-implemented` → `out-of-scope` (deliberate architectural choice, not a functionality gap).
