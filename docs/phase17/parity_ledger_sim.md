## Gaps summary

- ~~**No global-vs-local `ResourceTracker` model** (`TestAppAccounts`, `TestGlobalVsLocalResources`): algod-rust's `UnnamedResourcesAccessed` is a flat set of accessed resources; it has no per-txn-vs-group-shared assignment structure, no `Max*` capacity fields, and no cross-product (`MaxCrossProductReferences`) tracking at all. This cascades into every `TestUnnamedResources*` variant that reports resource *limits* rather than just *access*: `TestUnnamedResourcesCreatedAppsAndAssets`, `TestUnnamedResourcesCrossProductLimits`, `TestUnnamedResourcesLimits` (partial).~~ **Fixed** in issues #970 and #1005: `compute_resource_capacity` (`crates/core/algo-ledger/src/simulation/trace.rs`) computes the group-level `Max*`/`MaxCrossProductReferences` capacity fields (mirrors go's `makeGlobalResourceTracker`), and a shared `UnnamedCapacityTracker` (`avm_context.rs`) caps how many unnamed resources of each category get *reported* once that capacity is exhausted, including the created-app/asset cross-product exclusion `TestUnnamedResourcesCreatedAppsAndAssets` pins (#970). Issue #1005 closed the remaining gap: `is_account_available`/`resolve_asset`/`resolve_app`/`is_holding_available`/`is_local_available`/`available_app_box` now *reject the underlying AVM access* once capacity is exhausted, exactly like go's `ResourceTracker.add*` (an opcode that would fail in go with "unavailable Account ..."/"unavailable Asset ..."/"unavailable App ..."/"invalid Box reference ..." now fails the same way here, with go's exact error text) instead of always succeeding once `allow_unnamed_resources` is set. algod-rust still has no per-txn-vs-group-shared assignment structure (capacity is tracked at the group level only, not split local/global like go).
