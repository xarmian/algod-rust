## Gaps summary

- **No custom logging package port** (`TestCyclicWrite*`, `TestLogBuffer*`, `TestFileOutputNewLogger`, `TestSetGetLevel`, `TestSetLevelNewLogger`, `TestWithFieldsNewLogger`, `TestSetJSONFormatter`, `TestFatalExitHandler` — 13 tests): algod-rust uses the standard Rust `tracing`/`tracing-subscriber` ecosystem for structured logging instead of porting go-algorand's custom `logrus`-based `Logger`/`cyclicWriter`/`logBuffer` types. This is a deliberate architectural substitution (per `CLAUDE.md`), not a missing feature — rotation, level filtering, structured fields, and JSON formatting are all provided and tested by the upstream `tracing` crates rather than reimplemented and unit-tested in this repo.
- **No remote telemetry event-shipping pipeline** (`Test_loadTelemetryConfig` and all `telemetryConfig_test.go`/`telemetryhook_test.go`/`telemetry_test.go` tests, plus all of `telemetryspec/metric_test.go` — 28 tests): go-algorand ships structured operational events (block stats, transaction-processing-time distributions, session/heartbeat details, log mirroring) to a configurable remote monitoring backend via an async `logrus` hook and a `logging.config` file. algod-rust does not implement this subsystem at all. The only related algod-rust coverage is config-file compatibility, not a functional port: `crates/node/algo-config/src/lib.rs`'s `telemetry_to_log_defaults_true_and_round_trips` and `telemetry_only_fields_are_accepted_but_ignored_not_modeled` tests confirm that `config.json`'s `TelemetryToLog` and other telemetry-only keys parse without error but have no behavioral effect. Operational visibility in algod-rust is instead provided by a standard Prometheus `/metrics` endpoint (`crates/node/algo-rest-api/src/process_metrics.rs`, `crates/core/algo-agreement/tests/metrics_test.rs`), a functionally different, non-telemetry-event mechanism, so no 1:1 mapping exists.
- **Naming collision, not a match**: `TestHeartbeatDetails` (a telemetry-heartbeat-event detail struct) shares a name fragment with algod-rust's numerous `heartbeat`-prefixed tests in `algo-ledger`/`algo-validate`, but those implement the unrelated consensus `heartbeat` transaction type (challenge/PoS-style liveness proofs) and are not a parity match for this test.
