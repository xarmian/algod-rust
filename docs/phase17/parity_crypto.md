## Gaps summary

**BatchVerifier absent (13 tests: all of `batchverifier_test.go`, `gobatchverifier_test.go`).** algod-rust has no ed25519 batch-verification abstraction anywhere in `crates/` — it verifies signatures individually. This is a performance-design simplification, not a correctness gap (single-signature ed25519 verification is exercised extensively elsewhere, e.g. `algo-validate/src/signature.rs`), but it means none of Go's batch-specific edge cases (GC, mixed valid/invalid results, libsodium/Filippo/ed25519consensus cross-vectors) have a Rust analogue.

~~**State-proof *proving*/building role absent (`crypto/stateproof`, ~17 tests: `prover_test.go`'s Builder/Simulate/CoinIndex family, `weights_test.go`'s NumReveals/SigPartProofMaxSize, `coinGenerator_test.go`'s KATs).** algod-rust's `stateproof.rs` port implements verification only — there is no `Prover`/`Builder` type, no coin-index/cumulative-weight lookup, and no reveal-count-planning logic.~~ **Mostly closed** in issue #814: `stateproof.rs` now ports go's `Prover` (`prover.go`) — `make_prover`/`present`/`is_valid`/`add`/`ready`/`signed_weight`/`coin_index`/`create_proof`/`alloc_sigs` — plus `num_reveals` (`weights.go`'s reveal-count-planning search), exercised by a genuine multi-participant sign→build→verify round trip (`prover_builds_a_state_proof_that_verifies_with_partial_signers`) and per-error-path unit tests. Still not ported: `TestSimulateSignatureVerification*` (prover-side performance simulation) and `TestSigPartProofMaxSize` (proof-size bound estimation) — neither affects correctness of signing/proving itself, both are performance/capacity-planning helpers outside issue #814's signing-worker scope.

**No centralized ed25519 wrapper types (`SignatureSecrets`, `PrivateKey`, `PublicKey`, `Seed`, `Signature`, `ed25519PrivateKey/PublicKey/Seed/Signature` — ~22 msgp_gen rows, `out-of-scope`/`not-implemented`).** algod-rust uses `ed25519-dalek`'s own types directly at each call site rather than porting go-algorand's named msgp-wrapper structs, so this whole family of Go round-trip tests has no direct counterpart. Functionally equivalent coverage exists at the transaction-signature layer (`algo-validate/src/signature.rs`), but nothing at the bare-primitive level.

**Falcon-512 vs Falcon-1024 parameter-set mismatch.** algod-rust's `algo-falcon` crate and its "Falcon" test names throughout implement **Falcon-512**, while go-algorand's post-quantum signature scheme (state-proof participation keys, `pq_scheme_test.go`) is **Falcon-1024**. Signing/verification is implemented and tested in Rust, so these rows are marked `matched`/`partial` rather than `not-implemented`, but the parameter-set difference is flagged on every affected row and should be verified/reconciled — it is the single highest-priority factual finding in this audit. A few Falcon-specific behaviors (compressed-signature CT-format conversion, salt-version validation, verification-bytes accessor) have no Rust equivalent at all regardless of parameter set.

~~**No randomized/property-based msgpack encoding tests.** Every Go `TestRandomizedEncodingX` (msgp-generated, ~48 rows across `crypto`, `crypto/merklearray`, `crypto/merklesignature`) exercises round-trip encoding with randomized field values; Rust's equivalent round-trip tests consistently use fixed, hand-picked values instead. This is a systematic, low-risk-per-instance gap that a single `proptest`/`quickcheck`-style helper could close across many types at once, rather than needing one bespoke test per type.~~ **Mostly closed** across three issues, each adding a shared `ChaCha20Rng`-seeded, 1000-iteration driver matching go's `protocol.RunEncodingTest` iteration count: issue #826 theme 3 covered `crypto/merklearray`/`crypto/merklesignature`'s types with real, non-trivial-wrapper Rust structs (`tests/randomized_encoding_test.rs`); issue #956 extended the same treatment to the `crypto/stateproof` wire types `Reveal`/`StateProofBody`/`SigSlotCommit` (`algo-codec/src/canonical.rs`'s `canonical.rs` tests module, since those are the types with a real msgpack codec — `algo_consensus_crypto::stateproof`'s same-named types are verification-side structs with no codec of their own). ~~**Tamper/verification-failure vectors thinner than Go in the merkle-signature scheme (5 tests: TestBadRound, TestBadMerkleProofInSignature, TestIncorrectByteSignature, TestIncorrectMerkleIndex, TestAttemptToUseDifferentKey).**~~ **Fixed** in issue #826 theme 1 (PR #855) — all 7 new tests pass against the existing `verify_bytes` implementation with no code changes needed.

~~**Golden/known-answer-test (KAT) coverage missing across several crypto sub-packages** (`crypto/merklearray`'s TestMerkleTreeKATs/TestVCKATs, `crypto/merklesignature`'s TestGenerateKat, `crypto/stateproof`'s TestGenerateCoinHashKATs). See the updated rows above for exact status per test.

**Two architecturally out-of-scope go packages, correctly unwired.** `crypto/merkletrie` (23 tests including its `statetrie/nibbles` sibling) is fully implemented and tested in algod-rust under `algo-ledger`'s `merkle_trie.rs`/`merkle_cache.rs`/`merkle_committer.rs`/`merkle_page.rs` (matched-1:1/1:many for all 20 `merkletrie` tests); `crypto/statetrie/nibbles` itself is confirmed dead code in go-algorand v5.0.0-stable (no non-test call sites under `ledger/`/`trackers/`), so its 3 tests are legitimately `out-of-scope`.

**secp256k1 signing absent by design (6 of 9 tests `not-implemented`/`missing-test`).** algod-rust never signs with secp256k1 in production code — it only implements the AVM `ecdsa_verify`/`ecdsa_pk_recover`/`ecdsa_pk_decompress` opcodes, since secp256k1 signing isn't part of Algorand's account/consensus key model. Recovery-only coverage (`TestInvalidRecoveryID`, `TestRecoverSanity`) matches; the remaining sign-and/or-randomized-fuzz tests do not.
