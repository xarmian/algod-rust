## Gaps summary

- **Application-call excessive-rate-limiter (ERL) subsystem** (`data/appRateLimiter.go`, `TestAppRateLimiter_*`/`TestTxHandlerAppRateLimiter*` in `txHandler_test.go`): the *algorithm* is ported standalone (issue #821, PR #890, `crates/core/algo-pool/src/app_rate_limiter.rs`, all `TestAppRateLimiter_*` rows above). A third investigation pass found the wiring point the first two missed: algod-rust does have a genuinely unsolicited, peer-pushed transaction ingestion path — [`TxTagHandler`](../../crates/node/algo-network/src/tx_tag_handler.rs), the inbound gossip `TX`-tag handler registered on both the WS-gossip and libp2p P2P transports — the direct analogue of go's `TxHandler.processIncomingTxn`/`validateIncomingTxMessage`, the only two go call sites that invoke `incomingTxGroupAppRateLimit`. `TxTagHandler::with_app_rate_limiter` (attached in `bin/algod-rust/src/commands/participate.rs`, config-gated via `algo_config::Local`'s `EnableTxBacklogAppRateLimiting`/`TxBacklog*` fields, defaulting to go's v5.0.0-stable values) now gates admission by pool congestion + per-`(app, origin)` rate and penalizes eval-error failures, exactly as go does. algod-rust's pull-based `tx_syncer.rs` correctly remains unwired: re-tracing go's own pull-sync analogue (`rpcs.TxSyncer`/`data.SolicitedTxHandler`/`processDecoded`) confirms go itself never applies this gate there either — see `app_rate_limiter.rs`'s module doc for the full trace. The REST submission path remains correctly ungated too, matching go (`RawTransaction`/`RawTransactionAsync` both bypass `TxHandler`'s rate-limit checks).
- **`ElasticRateLimiter`/RED congestion management** (`util/rateLimit.go`, `TestTxHandlerAppRateLimiterERLEnabled`/`TestTxHandlerErlClientMapper`/`TestTxHandlerERLIPClient`/`TestTxHandlerAppRateLimiter_PenalizeEvalError`/`TestTxHandlerAppLimiter_NotPenalizeOutgoing`/`TestTxHandlerCapGuard` in `txHandler_test.go`): this is a **separate** subsystem from the app rate limiter above — go's `handler.erl`, not `handler.appLimiter`. Its *algorithm* is ported standalone (issue #860, `crates/core/algo-pool/src/elastic_rate_limiter.rs`, all `TestNewElasticRateLimiter`/`TestReservations`/`TestRED*` rows in `parity_util.md`). Unlike per-app rate limiting, this algorithm's *fairness* property (no single client can starve another's already-reserved capacity share) translates naturally onto algod-rust's pull-based servicing side rather than its push-gossip side: [`TxSyncPeerLimiter`](../../crates/node/algo-network/src/tx_sync_service.rs) applies it to how much of this node's own tx-sync *servicing* capacity each requesting peer's pull request may consume (the mirror image of go's inbound-admission gate), wired into `TxSyncService`'s HTTP endpoint and covered by dedicated fairness/congestion-toggle tests. go's own push-based ERL tests above still have no literal counterpart on `TxTagHandler` (ERL, unlike the app rate limiter, was not wired there), so they stay `not-implemented`/`partial` rather than `matched` — this is a faithful-fairness redesign, not a line-for-line port.
- **go's push-based gossip `TxHandler`** (`data/txHandler_test.go`, `data/txDupCache_test.go`): algod-rust's [`TxTagHandler`](../../crates/node/algo-network/src/tx_tag_handler.rs) is the real, if much simpler, counterpart for inbound `TX`-tag gossip messages (see the app-rate-limiter rows above); algod-rust additionally ingests transactions through a pull-based tx-sync design (`crates/node/algo-network/src/tx_syncer.rs`, `tx_sync_pool_adapter.rs`, `tx_sync_client.rs`) with no go equivalent. `TxTagHandler`'s much thinner backlog/seen-cache model still leaves message censoring, backlog-drop, salted-cache-rotation, and CapGuard tests with no corresponding rust tests.
- **`basics.Fraction`** (rational-number type, `fraction_test.go`) and **`basics.SError`** (structured/annotatable error type, `serr_test.go`) have no rust equivalents; algod-rust uses `thiserror`/`anyhow` idioms instead of a shared structured-error type.
- **`data/hashable.Message`** has no rust equivalent and none is warranted — issue #961 confirmed it has zero production callers in go-algorand itself (only its own generated test), so this stays `not-implemented`. **`data/stateproofmsg.Message`** does have a rust equivalent (`algo_types::StateProofMessage`) and now has dedicated msgpack round-trip tests (issue #961, see rows above).
- Several **participation-registry SQLite-internals tests** (`TestFlushDeadlock`, `TestFlushResetsLastError`, `TestParticipationDB_Locking`, `TestRegisterUpdatedEvent`, `TestAddingSecretTwice`) reflect go's specific SQLite-flush-goroutine/event-subscription implementation details that algod-rust's participation store (`crates/core/algo-ledger/src/participation/`) does not model the same way; most are `not-implemented` or `missing-test`.
- **`StateSchema`/`StateSchemas`, `ParticipationUpdates`, `BlockHeader`(direct), and `LightBlockHeader` msgpack-roundtrip tests** now have dedicated round-trip coverage (issue #961, see rows above). `StateSchemas` and `ParticipationUpdates` have no nested rust wire type — go's pairs/structs are represented as flat sibling fields on `ApplicationCallFields`/`BlockHeader` respectively — so their round-trips are exercised as part of the containing type's tests, noted per-row above.
- go's **reflection-based struct-field audits** (`TestBlockFields`, `TestAccountDataFields`) and **test-utility helpers** (`TestNearZeros`/`TestUnexported`/`TestMap` in `basics/testing`, `TestPow` in `txHandler_test.go`, `TestParticipationDB_Locking`) are `out-of-scope` — they exercise go-specific reflection or test-infra rather than portable protocol behavior.
