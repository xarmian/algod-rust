## Gaps summary

Status counts: matched-1:1 = 18, matched-1:many = 21, missing-test = 6, not-implemented = 41, out-of-scope = 4, partial = 29 (119 total).

- ~~**No state-proof worker/signing daemon (44 rows, the largest single gap
  group).**~~ **Core algorithm landed in issue #814** (`crates/core/algo-ledger/src/stateproof_worker.rs`):
  round-eligibility gates (`nextStateProofRound`, `signStateProof`'s
  interval check, `onlineProversThreshold`, `meetsBroadcastPolicy`),
  per-account signing (`signStateProofMessage`, reusing the existing
  `merklesig::Secrets`/`Signer` Falcon primitives), signature gathering
  (`SigCollector`, wrapping `algo_consensus_crypto::stateproof::Prover` —
  see `parity_crypto.md`'s state-proof-proving-role note) with go's
  `spProver.insertSig` exactly, and the `sigs` pending-signature table
  (`db.go`) via `rusqlite`.
  **The live daemon itself also now exists** (same issue, follow-on
  session, unblocked by issue #912's voters-participant-array
  persistence): `algo_ledger::stateproof_message::generate_state_proof_message`
  ports the signer-side `GenerateStateProofMessage`/`createHeaderCommitment`/
  `calculateLnProvenWeight`/`FetchLightHeaders` (a new
  `algo_consensus_crypto::light_block_header::LightBlockHeader` type
  supplies the SHA-256 vector-commitment-tree leaf go's
  `bookkeeping.LightBlockHeader` is); `stateproof_worker::StateProofRuntime`
  (`create_prover_entry`, `handle_sig`, `try_build`) is the in-memory
  equivalent of `Worker`'s `provers` map + `tryBroadcast`; and
  `bin/algod-rust/src/commands/stateproof_service.rs` wires it all into a
  background thread (mirroring `heartbeat_service.rs`'s established
  pattern, issue #820) that signs eligible rounds, gossips/gathers
  `SigFromAddr` messages over a new `Tag::StateProofSig` handler, and
  submits the resulting `StateProofTx` via `LocalTxBroadcaster` — gated
  behind `config.json`'s `EnableStateProofWorker` (default `false`, no go
  equivalent since go's `Worker` is always-on) rather than being wired
  into default node startup. **Deliberately still not ported**: a
  disk-persisted `provers` table (`stateproof/db.go`'s `provers` table,
  `TestProversDB`/`TestDbProverAlreadyExists`) — the runtime is in-memory
  only, rebuilt from the ledger's own persisted voters snapshot on
  restart — and go's `AcceptableStateProofWeight` incremental
  build-earlier-with-a-smaller-proof schedule (this runtime always
  targets the full proven-weight threshold, strictly safe but slower to
  produce the very first proof of a round). The remaining
  `not-implemented` `worker_test.go` rows are go's daemon-internal
  scenario tests this simplified in-memory implementation doesn't
  replicate one-for-one (DB-error injection, disk-cache-after-restart,
  `OnPrepareVoterCommit`/ledger-commit-triggered prover creation) — see
  each row's note. This is a distinct, previously-undocumented
  architectural gap — not covered by Phase 16 (which scoped only
  `config.Local`/`ConsensusParams`, not node subsystems).
- **`config.Local` node-runtime derivations still missing, even after the
  new `algo-config` crate.** Phase 16's original finding ("~58 of ~97
  `Local` fields have no equivalent at all") is significantly narrowed by
  `crates/node/algo-config` (76 tests covering versioned defaults,
  migration, JSON load/save, catchpoint-tracking gates, etc.), but several
  *behavioral* (not just field-storage) gaps remain unclosed: the full
  `IsListenServer`/`IsWsListenServer`/`IsP2PListenServer`/`IsHybridServer`
  state matrix, `AdjustConnectionLimits`/`RecalculateConnectionLimits`
  FD-pressure rebalancing, `ValidateP2PHybridConfig`, and the whole
  `EnsureAndResolveGenesisDirs`/`ResolveLogPaths` directory-resolution and
  hot/cold-data-dir-migration mechanism (7 config-package rows,
  not-implemented). The `HotDataDir`/`ColdDataDir`/etc. directory-splitting
  subset was explicitly dispositioned as an architectural non-goal by
  issue #749 (algod-rust's fixed two-file-pair storage design). The
  remaining behavioral derivations — `IsListenServer`/`IsWsListenServer`/
  `IsP2PListenServer`/`IsHybridServer`, `AdjustConnectionLimits`/
  `RecalculateConnectionLimits`, `ValidateP2PHybridConfig` — are genuinely
  untracked and filed as [issue #949](https://github.com/xarmian/algod-rust/issues/949).
- **No `phonebook.json` / `config.json.example` files.** go-algorand loads
  an optional phonebook include/exclude allow-list file and ships a
  `config.json.example` regression-checked against compiled defaults;
  algod-rust's in-memory `Phonebook` is populated only from DNS bootstrap,
  and no example config file exists to check. The `phonebook.json` loader
  is bundled into [issue #949](https://github.com/xarmian/algod-rust/issues/949).
- **No self-update mechanism.** `TestAlgodVsUpdatedVersions` tests
  go-algorand's S3-hosted-binary version-naming scheme; algod-rust ships no
  self-update mechanism at all (out-of-scope, architectural).
- **Whole-consensus-table invariant sweeps.** go's `TestConsensusParams`,
  `TestConsensusStateProofParams`, and the allocbound-vs-consensus-limit
  cross-check (`TestEncodedAccountAllocationBounds`) each iterate *every*
  known protocol version asserting a structural invariant holds throughout
  the table. [Issue #946](https://github.com/xarmian/algod-rust/issues/946)
  closed the first two: `crates/core/algo-types/tests/consensus_table_sweep_test.rs`
  now sweeps every `KNOWN_PROTOCOL_VERSIONS` entry asserting
  `TestConsensusParams`'s absolute-bound and grace-period invariants and
  `TestConsensusStateProofParams`'s state-proof key-capacity invariant, each
  backed by a TDD check proving the sweep catches a deliberately-introduced
  synthetic regression before trusting it against the real table.
  `TestEncodedAccountAllocationBounds` stays out-of-scope: it cross-checks
  fixed codec allocbound constants that have no counterpart in algod-rust's
  architecture (`rmp_serde` decodes into ordinary growable `Vec`/`HashMap`
  collections, not fixed-capacity allocbounds), so there is nothing for it
  to cross-check against. (Tracked together with the parallel AVM
  opcode/field table-completeness gap in `parity_txn_logic.md`.)
- **Go-reflection/codegen-specific test machinery has no Rust analogue
  (out-of-scope, `protocol`/`protocol/test`/`protocol/transcode`).** Tests
  like `TestEncodeInline`, `TestRandomizeObjectWithPtrField`,
  `TestCheckMsgpAllocBoundDirectiveCrossPackage`, and the `protocol/test`
  and `protocol/transcode` packages entirely test go-codec's
  reflection-based struct-tag machinery, its `msgp` codegen tool's
  `allocbound` directives, and a generic msgp↔JSON transcode CLI tool.
  algod-rust uses serde derive with hand-written canonical-encoding logic
  and explicit depth/size-limited decoders instead, so these have no
  meaningful port target; the underlying *properties* they protect
  (bounded allocation, round-trip correctness) are covered by different,
  more targeted Rust tests noted inline above.
- **PQ scheme registry only partially modeled.** go-algorand registers two
  PQ schemes (`PQSchemeFalcon1024`, `PQSchemeFalcon512`); algod-rust's
  `pq.rs` models only Falcon-1024, with no dedicated ASCII-printability/
  uniqueness invariant test for the scheme-tag byte pair.
- **`TestLockdownTagList` (backward-compat-locked message-of-interest tag
  allow-list) has no algod-rust equivalent** — a missing-test gap worth
  flagging since accidentally advertising a new tag to older peers is a
  real backward-compatibility hazard.
