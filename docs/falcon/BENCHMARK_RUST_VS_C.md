# Falcon-1024 `det1024`: Rust port vs. the vendored C library — benchmark

Register entry: `DIV-001` ([`docs/DIVERGENCES.md`](../DIVERGENCES.md)). Port
notes: [`FALCON_RUST_PORT.md`](FALCON_RUST_PORT.md). Measured 2026-10-14.

## Summary

| Operation | Verdict | Windows / MSVC | Linux / gcc |
|---|---|---|---|
| **sign** (32 B or 1000 B message) | Rust is **~15–16× faster** on both platforms | 16.5× | 15.2× |
| **keygen** (seed → key pair) | Rust is **~1.9–2.2× faster** on both platforms | 2.20× | 1.85× |
| **verify** | **Compiler-dependent, essentially parity.** Rust beats MSVC-compiled C by ~1.3×, but gcc-compiled C is ~7–8% faster than Rust | 1.32× faster | 0.94× (C 7% faster) |
| compressed → CT conversion | Parity (±12%, a few µs, once per signature) | 0.89× | 1.04× |

Why it matters in practice: signing is the only operation that sits on a
node's *own* hot path (state-proof signing, `algokey`), and it is where the
port wins by an order of magnitude. Verification is what the consensus path
runs for every Falcon signature a block carries (AVM `falcon_verify`, PQ
transactions, state proofs); there the port neither helps nor hurts —
**both backends produce bit-identical accept/reject decisions and error
codes** (see "Equivalence" below), so the choice is purely a performance and
build-toolchain one.

## What is compared

Both columns run the **same algorithm** and produce **byte-identical output**:

- **C**: `crates/core/algo-falcon/falcon-c/`, github.com/algorand/falcon
  v0.1.0 (Pornin's reference Falcon + Algorand's `det1024` layer) — the code
  go-algorand itself links through cgo — compiled by `build.rs` with
  `FALCON_FPEMU=1` (integer-emulated IEEE-754, no AVX2, no FMA), exactly the
  configuration go-algorand ships.
- **Rust**: `crates/core/algo-falcon/src/rs/`, a module-for-module port using
  native `f64` where the C emulates floating point (and the C's own
  fixed-point `expm_p63`).

Both are driven through the same public API
(`falcon_*_with(backend, …)`), so each measurement includes the crate's size
validation, buffer allocation and (for C) the FFI call — i.e. what a caller of
`algo_falcon` actually pays.

### Equivalence (the precondition for comparing speed)

A faster implementation is only interesting if it is the same function.
Evidence that it is, all in CI:

- `tests/fixtures/falcon/vectors.jsonl` — 113 records generated by
  **go-algorand itself** (`tools/falcon-vector-capture`, diffed in
  `falcon-vectors.yml`): keys, compressed and CT signatures, 28 must-reject
  inputs and go-algorand's own hard-coded verify vector, reproduced
  byte-for-byte by both backends (`tests/falcon_vectors.rs`).
- `tests/backend_parity.rs` — both backends on identical inputs: many seeds
  and message lengths, every seed length, a verify differential over mutated
  signatures / keys / messages (4,000 in the default test run, 150,000 per
  PR run of `falcon-parity.yml`, 1.5 million in its weekly run) requiring the
  full `Result<bool, FalconError>` to match,
  random bytes through CT/salt, malformed private keys
  (`.github/workflows/falcon-parity.yml`).
- 67 unit and per-module differential tests against the C internals
  (`cargo test -p algo-falcon --features c-internals-test`).

## Reading the results

**Signing: ~15–16× faster in Rust, on both platforms.** Falcon signing is
dominated by floating-point work (FFT, the ffLDL tree walk, and 2048
discrete-Gaussian samples per signature, each costing a few FP operations).
The C library is built with `FALCON_FPEMU=1` — every `+ − × ÷ √` is an
integer-arithmetic emulation of IEEE-754 — because that is how go-algorand
guarantees cross-platform determinism. The Rust port uses the hardware's
IEEE-754 `f64` and still produces the identical bytes (Rust's `+ − × ÷ √` are
correctly rounded, never fused, and the three places where the emulated and
native branches could differ are taken from the emulated one; see
[`FALCON_RUST_PORT.md`](FALCON_RUST_PORT.md)). A signature drops from
~8 ms to ~0.5 ms.

**Keygen: ~1.9–2.2× faster.** Key generation mixes the same floating-point
work (Gaussian sampling checks, Babai reduction) with a large amount of
multi-precision *integer* arithmetic (the NTRU solver). The FP part speeds up
like signing; the integer part runs at about C speed, so the overall gain is
smaller.

**Verification: parity, and which side wins depends on the C compiler.**
Verification is almost entirely integer work (three length-1024 NTTs, a
SHAKE256 hash-to-point, two decoders) — no floating point at all, so there is
nothing for the port to win by dropping the emulation. The result is therefore
decided by code generation: gcc compiles the C slightly better than LLVM
compiles the Rust (C ahead by 7–8% on Linux), while MSVC compiles the C worse
than LLVM compiles the Rust (Rust ahead by ~1.3× on Windows). **Both backends
verify in 40–60 µs, i.e. 17,000–25,000 verifications per second per core**;
that is not a bottleneck for a node.

**CT conversion** is a few microseconds of decode + re-encode and is
allocation-light in both; the differences are within ±12% and invisible at
the transaction level.

## Where the Rust verify time goes

Measured with a throwaway timing harness on the same machine (Windows, µs per
call, release profile; these are component timings, not Criterion):

| Component | µs |
|---|---|
| `mq_ntt` (one NTT, n = 1024) — run 3× per verify (public key, signature, inverse) | 8.3 |
| `hash_to_point` (SHAKE256 stream + reject sampling), after optimisation | 7.5 |
| `comp_decode` (signature) | 2.2 |
| `modq_decode` (public key) | 1.1 |
| everything else (norm check, allocation, resalt) | ~2–4 |

## Optimisation history (this port, Phase 21 stage 12)

| Change | Measured effect | Kept? |
|---|---|---|
| `hash_to_point_vartime_bulk`: pull every still-needed word out of SHAKE256 in one call instead of two bytes at a time (identical output stream) | 14.4 µs → 7.5 µs per hash (~7 µs off every verify and sign) | **yes** |
| Slice-based (`split_at_mut` / `chunks_exact_mut`) NTT/iNTT inner loops | NTT 8.3 µs → 9.7 µs (slower) | no, reverted |
| Hand-unrolled Keccak | not attempted: 0.42 µs per permutation is already at the scalar-implementation level (~10 cycles/byte) | n/a |
| Stack array for the CT-conversion coefficients | CT 5.0 → 4.5 µs | **yes** |

Remaining headroom on verify (not pursued): SIMD NTT with runtime CPU-feature
dispatch (SSE4.1/AVX2 `pmulld`). That would add `unsafe` and a dispatch layer
to a consensus-critical path for a gain no node needs today; it can be added
later behind the same corpus and differential tests.

## Caveats

- One machine, one run per platform. Treat sub-10% differences (verify, CT) as
  "equal"; the 15× signing and ~2× keygen gaps are far outside run-to-run
  noise (the confidence intervals in the tables are ≤ 4% wide).
- The Linux numbers come from a container in Docker Desktop's VM on the same
  CPU, so they include virtualization overhead — equally for both backends.
- The C library is deliberately benchmarked in go-algorand's configuration
  (`FPEMU`, no AVX2, no FMA). Enabling AVX2/FMA in the C would make signing
  faster but changes the floating-point results' determinism guarantees and is
  not what go-algorand ships.
- Constant-time behaviour is not measured here. The Rust port keeps the C's
  constant-time constructs on secret-dependent paths but they are not
  separately audited; determinism/bit-identity is the tested property
  (`docs/PHASE21_VALIDATION.md`).
- End-to-end node throughput is unaffected at the percent level: a block's
  Falcon verifications are tens of microseconds each.

## Reproduce

```bash
# Windows / any host with a C toolchain
cargo bench -p algo-falcon
python3 scripts/falcon_bench_report.py            # renders the tables above

# Linux in Docker (what produced the second table)
docker run --rm -v "$PWD:/src:ro" -v falcon-bench-target:/target \
  -e CARGO_TARGET_DIR=/target -e CARGO_HOME=/target/cargo-home -w /src \
  rust:1.93-bookworm cargo bench --locked -p algo-falcon
# then copy /target/criterion out of the volume and:
python3 scripts/falcon_bench_report.py <criterion-dir>
```

Run a single backend with the Criterion filter, e.g.
`cargo bench -p algo-falcon -- "sign/32B/rust"`.
