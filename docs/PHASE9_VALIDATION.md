# Phase 9 Validation — go-algorand v4.6.0-stable Parity

_Completed: 2026-08-24 (revised same day — epic reopened after a completeness re-check found release-scoped follow-ups #518/#519 had been left open at first close-out; both are now resolved, see below)_

This document is the evidence map for [`docs/PHASE9_PROPOSAL.md`](PHASE9_PROPOSAL.md) and epic [#503](https://github.com/xarmian/algod-rust/issues/503)'s acceptance criteria. Every claim below cites a specific PR, test, or CI run.

## Summary

Moved algod-rust's parity target from go-algorand `v4.5.1-stable` (`a8c16ecc2324cc10acb75de367c0b5dad4b0a5a3`) to `v4.6.0-stable` (`0915527b4c462381d9afeabcd697703c9fbf61f9`). The release carries **no consensus/protocol version upgrade** — go-algorand's own release notes confirm this, and stage 2's analysis found zero changes touching `agreement/**` semantics, `config/consensus.go`, `data/transactions/logic/**`, or block/encoding formats. Every in-scope item is REST-surface or an infrastructure constant; nothing here required live mixed-cluster (agreement/consensus) verification, only REST-level dual-node conformance.

## Not-applicable items (no live/mixed-cluster verification needed)

Thirteen of the nineteen upstream PRs in the `v4.5.1-stable..v4.6.0-stable` range were classified `not-applicable` at stage 2 (see epic #503's full inventory for per-item justification): one pure-refactor `agreement/` change, nine changes to go-algorand's experimental libp2p P2P transport (which algod-rust does not implement), one internal Go I/O-scheduling optimization, one `kmd`-only fix (out of algod-rust's current scope), one test-only change, and one Go build-tooling change. None of these required a mixed-cluster consensus soak — this epic's only live verification need was REST-level dual-node conformance (satisfied by the `Dual-Node REST Conformance` CI workflow on every REST-touching PR) plus, for the two consensus-adjacent ledger fixes (#518, #519), a real mixed-cluster/dual-node live run each.

## Completeness re-check (2026-08-24, epic reopened)

The epic was first closed on 2026-08-24 with #518 and #519 still open, tracked as "not blocking." On reopening, two corrections were made, both now reflected in this document and in epic #503:

1. **Release-notes completeness.** Re-fetching the live upstream release notes (`gh api repos/algorand/go-algorand/releases/tags/v4.6.0-stable`) and cross-checking all 19 listed PRs against the original inventory found 3 that were never listed: [#6572](https://github.com/algorand/go-algorand/pull/6572), [#6554](https://github.com/algorand/go-algorand/pull/6554), [#6562](https://github.com/algorand/go-algorand/pull/6562) — all three touch only `network/p2p/**`, the same experimental libp2p transport as the other 6 already-classified P2P items, so their correct disposition (`not-applicable`) was already established by pattern. This was a documentation gap, not a missed implementation requirement — no code changes resulted. The `algod-version-upgrade` skill was updated ([PR #522](https://github.com/xarmian/algod-rust/pull/522)) to require this cross-check explicitly on any future release-notes review, including a re-review before closing a reopened epic.
2. **Release-scoped follow-ups must be worked, not just tracked.** #518 and #519 were both surfaced directly by #508's new `online-stake` field and share its underlying accessor — reclassified from "tracked, not blocking" to required, and both run through `algod-issue-fix` to completion (PRs #524, #525) before this second close-out. The skill now has a hard gate (`gh issue list --label phase:9 --state open` must be empty) enforcing this going forward.

Two further findings surfaced during #518/#519's live verification (#523: a pre-existing `online-money`/`total-money` accounting bug; #526: dev-mode never sweeps expired participation keys offline) were judged genuinely out of scope — neither field/behavior is new or changed in v4.6.0-stable — and were explicitly *not* added to this epic's blocking list, per the skill's judgment-call rule (a finding blocks the epic only if the release's own changes caused or newly surfaced it, not merely because the release's own verification work happened to walk past it). Both remain tracked as ordinary bugs outside this epic.
