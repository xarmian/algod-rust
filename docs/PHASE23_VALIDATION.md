# Phase 23 Validation — reproducible Go vs Rust benchmark, then parity-safe optimization

_Written 2026-11-09, updated 2026-11-12 (epic #2101 closed; every child and follow-up issue closed except #2110, which this record closes; see "Known limitations")_

Evidence map for [`docs/PHASE23_PROPOSAL.md`](PHASE23_PROPOSAL.md). Tracking
epic: [#2101](https://github.com/xarmian/algod-rust/issues/2101); the
optimization pass is [#2110](https://github.com/xarmian/algod-rust/issues/2110),
recorded in [`docs/PERF_PHASE23.md`](PERF_PHASE23.md); the published baseline is
[`docs/BENCHMARK_RESULTS.md`](BENCHMARK_RESULTS.md).

Phase 23 is a benchmarking and performance phase: it changes no go-algorand
pin and adds no protocol feature. Its parity evidence is therefore (a) the
equality gates every macro tier asserts and (b) the parity guard each
optimization names. This file states honestly which acceptance criteria are met
and which are not.

## Work after the first version of this record

- **WAL fixes.** #2208 (checkpoint the tracker WAL when a read snapshot opens,
  DIV-008) was joined by #2299, which bounds the block archive WAL (found by the
  Docker `catchup` measurement: 248 MB beside a 4 MB block file; same DIV-008
  entry), and #2211 (archive commit before the tracker commit, DIV-009).
- **Simulate.** The `rest` tier showed simulate at 0.22x of go. The root cause
  (#2282) was a SAVEPOINT in autocommit mode: `restore_snapshot` committed the
  rolled-back writes and synced the WAL on every request. After the fix a CI
  `rest` smoke has Rust ahead of go (2,799 vs 2,434 req/s). Simulate at a past
  round (#2148) is served from an in-memory undo journal, registered as DIV-007.
- **Catchpoint-start replay corpus (#2146).** Testnet catchpoint 69120000,
  rounds 69120001..69120200 (proposer payouts in every block, a state proof at
  69120131, 257 app calls): fetched with a lookback, coverage-gated, started by
  go through `CatchpointCatchupAccessor` and by algod-rust through the
  production sync flow, final-state equality gated, wired into the `replay`
  tier (PRs #2294 to #2297).
- **Docker `catchup` tier findings.** The tier had reported algod-rust replaying
  at 26.5 vs go 107 blocks/s. The apply thread never waited for a fetch and used
  20 % of one core; the time was SQLite file operations on a Docker Desktop
  bind mount (about 2 ms per write commit, 0.3 ms per read transaction, 5 ms per
  connection open; a named volume 0.01 / 0 / 0.04 ms). With `/data` on a named
  volume the tier shows 105 vs go 118 blocks/s (n = 3), and the commit before
  #2203 reproduces the original gap (24.7 vs go 131.6). The tier keeps `/data` in
  a named volume off Linux (`BENCH_CATCHUP_DATA_MOUNT`, PR #2300). The same
  measurement is where the second WAL (above) and the absence of the RSS excess
  were established. `blockio_write_mb` is not meaningful on Docker Desktop.
- **Mixed-cluster TX gossip harness (#2154, #2280).** `PHASE6_TOPOLOGY=rust-relay|go-relay`
  isolates a Go participation node behind one relay (a Rust relay, or a Go relay
  as the control), `tx_gossip.py` and `tx-gossip-topology.sh` check every pair and
  verify the isolation from the Go nodes' own connection logs; a dispatch-only
  workflow runs both legs (PRs #2281, #2302, #2303, #2305). Along the way the
  harness had four bugs fixed: ports still bound between repetitions, the slow
  per-txid pending endpoint of go (#2301 was not a node defect: the Rust node
  forwards within 3 ms of a submit), a POST that itself takes seconds on a Go
  node, and a stale `kmd.pid` that made `goal kmd start` SIGTERM the Go node
  container. #2304 (the Rust `GET /v2/transactions/pending` JSON used integer
  arrays for byte fields) was a real node parity bug found the same way and is
  fixed (PR #2306).

## Parity findings surfaced by the gates (fixed under this label)

The equality gates and the corpus work were not only a speed measurement; the
issues below were found by them or while reading go to explain a number, and
are fixed: rewards pool never debited (#2116), `checkDup` in validate mode and
on the pool/gossip paths (#2127, #2129, #2130, #2184, #2186, #2187, #2217),
simulate round selection, duplicate rejection and response shape (#2118, #2123,
#2125, #2160, #2161, #2178), `/v2/accounts` and `/v2/transactions/params` fields
(#2155 to #2158, #2171), certificate step encoding (#2159), admission rules
(#2193, #2196 to #2198, #2218), `ecdsa_pk_recover` argument order (#2253) and
`sumhash512` version (#2255), participation nodes not receiving TX gossip
(#2150), and several sync lifecycle bugs (#2137 to #2141, #2143, #2144, #2209).

## Known limitations / sign-offs

- **A full post-optimization `make bench-compare` re-run on quiet dedicated
  hardware was NOT done**, and `BENCHMARK_RESULTS.md` still carries the
  pre-optimization baseline (one desktop in WSL2, n = 3, smoke profiles for
  `rest` and `localnet`; indicative, not authoritative). The post-optimization
  numbers are per hotspot in `PERF_PHASE23.md`, on different hosts, some n = 1
  (stated per row); the Docker `catchup` tier is the one tier re-run after the
  optimizations (n = 3, 2026-11-11, Docker Desktop on Windows).
- The Docker `catchup` rows are Docker Desktop on Windows with `/data` on a named
  volume: relative numbers within a run are meaningful, absolute ones are not
  comparable with the Linux CI host.
- `blockio_write_mb` of the `catchup` tier is not a usable metric on Docker
  Desktop (the cgroup counter does not see the VM-level I/O).
- The codec / certificate / proposal decode gaps of the baseline (row 9) were
  never profiled or optimized.
- Batching the tracker commit during catchup (what go does, and what would help
  algod-rust on slow file-sharing layers) is not built: it changes the DIV-009
  crash model.
