## 2. Executive summary

This is the inaugural deep security and consensus-parity audit under `audits/instructions.md` v2.0, covering `A-00 Delta` (recent Phase 21/22 commits in `crates/core/**`) and four foundational Tier-1 crates: `A-01` (`algo-codec`), `A-02` (`algo-types`), `A-03` (`algo-validate`), and `A-10` (`algo-abi`). Overall engineering quality across these four crates is high: canonical msgpack encoding, domain-separated hashing (`TX`, `TG`, `BH`, `STIB`, `TL`, `MA`, `MB`, `Program`, `MsigProgram`, `PQProgram`, `PQA`, `OT1`, `OT2`, `SD`), libsodium `bv_compatible` Ed25519 signature verification, 192-bit `mul2div_u64` fee arithmetic, and protocol-aware genesis field restoration are carefully engineered and backed by 924 unit tests and 30 integration test suites (all passing).

However, side-by-side differential analysis (`M1`) and ingress-to-sink tracing (`M2`/`M6`/`M8`) uncovered **seven concrete findings** (**1 High**, **3 Medium**, **2 Low**, **1 Informational**):
1. **`[FIND-ba9c86e5-01]` (🟠 High, Confirmed — `algod-rust only`):** In `algo-validate`, `bin/algod-rust` (`SimpleBlockEvaluator`), and `algo-ledger::simulation`, `logic_sig_group_size_check` is **not called** during pool admission, `verify_transaction_group_cached`, or `/v2/transactions/simulate` (`check()`). Consequently, a transaction group with pooled LogicSig arguments exceeding `len(group) * LogicSigMaxSize` (at v40+) is **accepted into the mempool, cached in `VerifiedTransactionCache`, and reported as passing in `simulate`**, only to fail block validation (`validate_block`) when proposed. Furthermore, `verify_transaction_signature_with_tracer` checks `stx.lsig.is_some()` instead of `go-algorand`'s `s.Lsig.HasProgram()` (`len(logic) != 0`), causing consensus/validation divergence on transactions carrying an empty-program `LogicSig` struct on pre-v42 protocols. (`go-algorand` `verify/txn.go:L238-L357` calls `logicSigGroupSizeCheck` on every group verification and checks `s.Lsig.HasProgram()`.)
2. **`[FIND-ba9c86e5-02]` (🟡 Medium, Confirmed — `algod-rust only`):** Inbound gossip transaction decoding (`TxTagHandler::decode_tx_message` in `algo-network`) uses `rmp_serde::from_read::<_, SignedTransaction>` without calling `check_msgpack_depth` (255-level nesting cap) and without using the hand-rolled `SignedTransaction::decode_from_reader` that enforces `go-algorand`'s `codec:",required"` checks (`type`, `snd`, `msig.v/thr/subsig`). This allows deeply nested msgpack payloads in `dt` (`eval_delta`) or unknown keys to recurse on the async worker stack, and allows zero-sender/empty-type gossip messages to evade peer disconnection (`ForwardingPolicy::Disconnect`). (`go-algorand` `msgp_gen.go:L5580-L5670` enforces `st.AllowableDepth = 255`, rejects unknown/block-only fields, and checks `Txn.MsgIsZero()`.)
3. **`[FIND-ba9c86e5-03]` (🟡 Medium, Confirmed — `both go-algorand and algod-rust`):** Both `algo-abi` (`crates/core/algo-abi/src/lib.rs`) and `go-algorand`'s upstream `github.com/algorand/avm-abi v0.2.0` (`abi/type.go:L443`, `abi/encode.go:L35-L49`) perform unchecked integer multiplication in `ByteLen()` (`elem.byte_len()? * len` in Rust; `int(t.staticLength) * elemByteLen` in Go) that overflows on nested static array types (e.g. `uint64[65535][65535][65535]`), and both expand static/dynamic array types into `Vec<AbiType>` / `[]Type` slices (`vec![(**elem).clone(); *len]` in Rust; `typeCastToTuple` in Go) before checking payload length, enabling memory amplification via the `abi:` box-name query parameter on REST endpoints (`GET /v2/applications/{id}/box` and `/boxes`). Additionally, `go-algorand`'s `TypeOf` (`abi/type.go:L102`) has no recursion-depth cap at all (`algod-rust` caps `MAX_ABI_DEPTH = 64`), whereas `algod-rust` panics in debug mode on the `usize` multiply overflow where Go wraps silently.
4. **`[FIND-ba9c86e5-04]` (🟡 Medium, Confirmed — `algod-rust only`):** `Simulator::check()` in `algo-ledger/src/simulation/mod.rs` checks group fees using a legacy flat `min_fee_count * consensus.min_txn_fee` calculation instead of `algo_validate::fee::check_submitted_group_fees` (`SummarizeFees` + `FeeForUsage`). Under v42+ (`TxnSizePricingEnabled`) or PQ signatures (`PQSig`), `simulate` accepts groups that underpay their size-pricing or Falcon-1024 fee surcharge during `check()`. (`go-algorand` `simulator.go` runs `eval.CheckGroupFees` which uses `SummarizeFees` + `FeeForUsage`.)
5. **`[FIND-ba9c86e5-05]` (🔵 Low, Confirmed — `algod-rust only`):** `LogicSig::blank()` check in `logic_sig_group_size_check` (`crates/core/algo-validate/src/signature.rs:1264-1273`) and `Simulator::check()` (`crates/core/algo-ledger/src/simulation/mod.rs:1019-1025`) omits `l.pqsig.is_none()`, whereas `go-algorand`'s `LogicSig.Blank()` (`data/transactions/logicsig.go:53-56`) checks `lsig.PQsig.Blank()`. Also, `LogicSig::decode_from_reader` unconditionally rejects a `LogicSig` map that omits `"l"`, whereas `go-algorand`'s `LogicSig.UnmarshalMsgWithState` does not mark `"l"` as `codec:",required"` at msgpack decode time (deferring orphan-`LogicSig` handling to `logicSigGroupSizeCheck`).
6. **`[FIND-ba9c86e5-06]` (🔵 Low, Confirmed — `algod-rust only`):** `serde_raw_str::serialize` in `crates/core/algo-types/src/serde_bytes_array.rs:321` contains an `unsafe { std::str::from_utf8_unchecked(v) }` that violates Rust's `&str` UTF-8 validity invariant when `AssetParams` with non-UTF-8 `unit_name`/`asset_name`/`url` is serialized through `serde`. (Go strings do not have a language-level UTF-8 memory-safety invariant.)
7. **`[FIND-ba9c86e5-07]` (⚪ Informational, Confirmed — `algod-rust only`):** `check_msgpack_depth` (`crates/core/algo-types/src/rmp_decode.rs:95-98`) only checks the *first* msgpack value in `bytes`, so `decode_signed_txn_stream` in `algo-codec` redundantly parses each stream element twice (`skip_value` + `rmp_serde`). (`go-algorand`'s `msgp` tracks `AllowableDepth` inline during a single-pass decode.)

## 4. Findings

### [FIND-ba9c86e5-01] Missing `logic_sig_group_size_check` on Pool/Cache/Simulate Paths and `HasProgram()` vs `is_some()` Divergence on Empty-Program `LogicSig`
- **Severity:** 🟠 High · **Impact:** High · **Likelihood:** High · **Confidence:** Confirmed
- **Affected implementations:** `algod-rust only` (`go-algorand v5.0.4-stable` enforces `logicSigGroupSizeCheck` on all paths and checks `s.Lsig.HasProgram()`)
- **Property:** P1 (State-transition equivalence), P4 (Smart-contract platform integrity), P8 (Developer-tooling fidelity) · **Adversary:** T2 (Transaction submitter) / T4 (Byzantine proposer) · **Area:** A-03 · **Category:** Consensus parity / Contract rule / Tooling fidelity
- **Location:**
  - `crates/core/algo-validate/src/signature.rs:L1168-L1196` (function `verify_transaction_signature_with_tracer`)
  - `crates/core/algo-validate/src/verified_txn_cache.rs:L412-L462` (function `verify_transaction_group_cached_inner`)
  - `bin/algod-rust/src/commands/participate.rs:L1693-L1855` (function `SimpleBlockEvaluator::validate_group_stateless_inner`)
  - `crates/core/algo-ledger/src/simulation/mod.rs:L1012-L1245` (function `Simulator::check`)
- **Upstream reference:** `../go-algorand/data/transactions/verify/txn.go:L231-L357` (functions `txnGroupBatchPrep`, `logicSigGroupSizeCheck`, `checkTxnSigTypeCounts`)
- **Risk registry:** `RISK-INT-001`, `RISK-INT-027`, `RISK-INT-029`, `RISK-INT-030`
- **Duplicate of:** none
- **Status:** Open

#### Description & root cause
**Implementation scope:** This issue exists **only in `algod-rust`** (`go-algorand v5.0.4-stable` is not affected).

There are two coupled defects in how `algod-rust` validates `LogicSig` group size limits and signature categories compared to `go-algorand`'s `verify.TxnGroup` (`../go-algorand/data/transactions/verify/txn.go:L218-L357`):

**Part A — Missing `logic_sig_group_size_check` in Pool Admission, `VerifiedTransactionCache`, and `Simulator::check()`:**
In `go-algorand`, `txnGroupBatchPrep` (`verify/txn.go:L238-L240`) runs `logicSigGroupSizeCheck(stxs, groupCtx)` on **every** transaction group verification — including mempool admission, gossip `StreamToBatch` verification, block validation, and `/v2/transactions/simulate`.
In `algod-rust`:
1. When `enable_logicsig_size_pooling` is `true` (consensus v40+), `verify_logicsig_with_tracer` (`crates/core/algo-validate/src/signature.rs:L712-L724`) skips the per-transaction `lsig_len > consensus.logic_sig_max_size` check, deferring to `logic_sig_group_size_check`.
2. However, `logic_sig_group_size_check` is **only** called inside `validate_block_with_cache` (`crates/core/algo-validate/src/block.rs:L599`).
3. It is **never called** in:
   - `verify_transaction_group_cached_inner` (`crates/core/algo-validate/src/verified_txn_cache.rs:L412-L462`),
   - `SimpleBlockEvaluator::validate_group_stateless_inner` (`bin/algod-rust/src/commands/participate.rs:L1693-L1855`), or
   - `Simulator::check` (`crates/core/algo-ledger/src/simulation/mod.rs:L1012-L1245`, which only duplicated the orphan-content sub-check at `L1018-L1034`, omitting the pooled `lsig_args_size > lsig_available_pool` and pre-v42 `lsig_pooled_size > lsig_available_pool` checks!).

As a result:
- A transaction group at v40–v43 carrying a valid `LogicSig` whose arguments exceed the group pool (`lsig_args_size > group.len() * 1000`, e.g., a singleton transaction with one 2,000-byte argument, which passes the 4,096-byte `MAX_LOGIC_SIG_ARG_SIZE` per-arg check) **passes** `BatchVerifier`, **passes** `SimpleBlockEvaluator::validate_group_stateless_inner`, is **inserted into `VerifiedTransactionCache` as verified**, and is **admitted into the transaction pool and proposed in a block by `algod-rust`**! When that proposed block is validated by peers (or by `algod-rust`'s own `validate_block`), `logic_sig_group_size_check` rejects the block (`RISK-INT-029`).
- In `/v2/transactions/simulate`, the same oversized-arg `LogicSig` group is accepted and simulated as succeeding, whereas `go-algorand`'s `simulate` rejects it in `check()`.

**Part B — Consensus Divergence on Empty-Program `LogicSig` (`has_lsig` vs `s.Lsig.HasProgram()`):**
In `go-algorand`, `checkTxnSigTypeCounts` (`../go-algorand/data/transactions/verify/txn.go:L322-L337`) checks:
```go
if !s.Sig.Blank() {
    numSigCategories++
    sigType = regularSig
}
if !s.Msig.Blank() {
    numSigCategories++
    sigType = multiSig
}
if s.Lsig.HasProgram() { // len(s.Lsig.Logic) != 0
    numSigCategories++
    sigType = logicSig
}
if !s.PQsig.Blank() {
    numSigCategories++
    sigType = pqSig
}
```
Notice that `go-algorand` checks `s.Lsig.HasProgram()` (`len(s.Lsig.Logic) != 0`), **not** `!s.Lsig.Blank()`.
On pre-v42 protocols (`!TxnSizePricingEnabled()`, e.g. v40 and v41), if a transaction has a valid `Sig` (or `Msig`) AND also carries a non-blank `Lsig` with an **empty program** (`Logic == []`, e.g. `Lsig.Sig` or `Lsig.Args` populated):
- `go-algorand`'s `logicSigGroupSizeCheck` (`verify/txn.go:L264-L275`) sees `!lsig.HasProgram()`, checks `rejectOrphanLSigContent` (`false` pre-v42), and either skips it (`!poolOrphanLSigArgs` at v40/v41) or pools its args.
- `go-algorand`'s `checkTxnSigTypeCounts` sees `s.Lsig.HasProgram() == false`, so `numSigCategories == 1` (`regularSig`), verifies `s.Sig`, and **accepts the transaction**.
- In `algod-rust` (`crates/core/algo-validate/src/signature.rs:L1168-L1172`):
  ```rust
  let has_sig = stx.sig != [0u8; 64];
  let has_msig = stx.msig.is_some();
  let has_lsig = stx.lsig.is_some();
  let has_pqsig = stx_pqsig_present;
  let count = has_sig as u8 + has_msig as u8 + has_lsig as u8 + has_pqsig as u8;
  ```
  Because `stx.lsig` is `Some(...)`, `has_lsig` is `true`, making `count == 2`, and `algod-rust` **rejects** the transaction with `"signedtxn should have only one type of signature, found 2"`.

#### Exploit scenario / proof of concept
See `audits/poc/2026-10-23_105644_claude-opus-4-8_ba9c86e5/README.md` §1a and §1b for full runnable Rust tests:
1. **Liveness / Invalid Block Proposal (v42/v43):** An attacker T2 submits a transaction authorized by a contract-account `LogicSig` (`#pragma version 1; int 1`, 5 bytes) with a single 2,000-byte argument (`arg[0] = [0x11; 2000]`). It passes `decode_tx_group`, `BatchVerifier`, and `SimpleBlockEvaluator::validate_group` because none of them call `logic_sig_group_size_check`. When the `algod-rust` node is selected as block proposer, `SimpleBlockEvaluator::generate_block` includes this transaction in the proposed block. Every `go-algorand` peer (and `algod-rust`'s `validate_block`) rejects the proposal with `"txgroup had 2000 bytes of LogicSig args, more than the available size pool of 1000 bytes"`.
2. **Pre-v42 Validation Divergence:** On a v40 or v41 block/replay test (or custom `consensus.json` protocol with `per_byte_txn_surcharge == 0`), a transaction signed with `sig` that also includes `"lsig": {"l": b"", "arg": [b"x"]}` is accepted by `go-algorand` and rejected by `algod-rust`.

#### Impact on builders
Smart-contract developers testing a multi-transaction atomic group with `LogicSig` arguments via `/v2/transactions/simulate` (or submitting it to the mempool) will see `algod-rust` accept a group whose total `LogicSig` arguments exceed `len(group) * 1000` bytes, whereas MainNet consensus (`validate_block` and `go-algorand`) rejects it. Even worse, an `algod-rust` validator can be tricked into proposing an invalid block that the network rejects.

#### Remediation
1. Call `logic_sig_group_size_check(txgroup, consensus)` inside `verify_transaction_group_cached_inner` (`crates/core/algo-validate/src/verified_txn_cache.rs:L455`), inside the non-cached fallback in `SimpleBlockEvaluator::validate_group_stateless_inner` (`bin/algod-rust/src/commands/participate.rs:L1790`), and inside `Simulator::check` (`crates/core/algo-ledger/src/simulation/mod.rs:L1018`, returning `CheckOutcome::RecoverableFailure`).
2. In `verify_transaction_signature_with_tracer` (`crates/core/algo-validate/src/signature.rs:L1168-L1196`), match `go-algorand`'s `checkTxnSigTypeCounts`: count `has_lsig` as `stx.lsig.as_ref().is_some_and(|l| !l.logic.is_empty())` and `has_msig` as `stx.msig.as_ref().is_some_and(|m| !m.is_blank())`, once `logic_sig_group_size_check` has already screened orphan `LogicSig` fields.

### [FIND-ba9c86e5-02] Gossip `decode_tx_message` Uses Unbounded `rmp_serde` Instead of Depth-Checked `SignedTransaction::decode_from_reader`

## 9. Open questions & not covered

1. **Struct-from-array msgpack decoding (`msgp` array-encoded structs):** `go-algorand`'s generated `msgp_gen.go` decoders include a fallback branch `if _, ok := err.(msgp.TypeError); ok { zb, _, bts, err = msgp.ReadArrayHeaderBytes(bts) ... }` that allows msgpack *arrays* to decode into Go structs positionally unless canonical-reencode checks reject them. `algod-rust`'s `decode_from_reader` only accepts msgpack *maps*. On P2P/block paths where canonical encoding is required (`strict_canonical_reencode_check`), array-encoded structs are rejected by Go as non-canonical anyway; however, during future `A-15` (WebSocket gossip) and `A-18` (REST API) audits, verify whether any non-canonical msgpack test or client relies on struct-from-array decoding.
2. **Recommended next audit scope:** `A-04` (`algo-ledger` — Ledger apply & block evaluation), `A-06` (`algo-avm` — AVM core: parser, flow, stack, budgets), and `A-07` (`algo-avm` + `algo-ledger` — AVM state, resources, boxes, inner txns) are the highest-priority remaining Tier-1 areas.
